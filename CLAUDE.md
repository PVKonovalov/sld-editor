## What this is

A monorepo SCADA-style Single Line Diagram (SLD) editor for Power/Energy control engineers

## Project state

Stages 1-3 are implemented: backend core API, frontend shell UI, and interactive canvas editing (select/multi-select/drag/click-to-place/click-to-connect/copy-paste/delete). A shape can declare its own real terminal points (`elements.Symbol.Terminals`, only the Breaker so far) — shown as a small red "X" on the current selection, blue on hover — and `Canvas` now also has a proper click-to-route wiring tool (click a terminal, click to bend, click a target — another terminal, or any point along a busbar — to finish, double-click to end in mid-air, Esc to cancel; see `Canvas`'s `routing` state and `diagramOps.drawConnectorPath`/`drawDanglingConnectorPath`) alongside the older instant Ctrl/Cmd-click-connect (`connectElements`, still anchor-to-anchor only, unchanged). An already-drawn connector can also be reshaped directly — select it to get a filled-square handle at each interior bend point and a semi-transparent circle at each segment's own midpoint (drag a vertex to move it orthogonally, drag a midpoint to insert a new bend, double-click the line to add one directly, select a vertex and Delete/Backspace to remove just it; see `diagramOps.moveConnectorVertex`/`insertConnectorVertex`/`removeConnectorVertex`/`simplifyOrthogonalPath`). Deletion also has two granularities now ("Piece B"): right-clicking a connector offers "Delete segment" (splits it into up to two independent connectors at the clicked segment, via `diagramOps.deleteConnectorSegment` — either side is dropped instead if the cut would leave it a single point) alongside "Delete wire" (the old whole-connector removal); any connector end left unreferenced by an element's Port — from a segment cut or from ending a route in mid-air — gets a persistent red dashed outline along the connector plus a small red-dot marker at that end that removes the whole connector in one click (`diagramOps.usedNodeIds`/`danglingConnectorEnds`). Dragging an element (or a multi-selected group) now also re-routes whatever's attached to it ("Piece C", endpoint-follows-only — the simplest useful version, not full accordion re-layout): a connector with both ends on elements moving together translates as a rigid whole, one with only one end attached instead has just that end follow, with the touching segment kept orthogonal the same projection-lock way an interior vertex drag already is (`diagramOps.moveElements`). Not yet built: a 45°/manual-bend-axis routing mode, re-routing when a BusBarSection's own single-endpoint drag handle moves instead of a whole-element drag, importing an existing xsde2svg-style SVG (sld-svg's `extract` side of the format was deliberately not ported — see `internal/slddoc/doc.go`), and undo/redo.

Reference repos on disk that this project's design follows: `sld-svg` (sibling repo) defines the canonical `slddoc` XML format and is the source `internal/slddoc` was ported from (its own copy lives under `sld-svg/internal/`, so it can't be imported across module boundaries — see that package's own doc comment); `sld-viewer` (sibling repo) is the UI/UX and backend-stack reference (React+Vite+TS+Tailwind+lucide-react frontend; Gin+YAML-config backend), though it's a full DB-backed SCADA viewer and much heavier than what this editor needs.

Run the backend from `backend/`: `go run ./cmd/sld-editor -config config/sld-editor.yaml` (binds `0.0.0.0:8090` by default). Build/vet/test: `go build ./...`, `go vet ./...`, `go test ./...`, all from `backend/`.

Run the frontend from `frontend/`: `npm install` once, then `npm run dev` (Vite dev server on `:5173`, proxying `/api` to `:8090` — the backend must already be running). Type-check + production build: `npm run build`.

## Structure

- `backend/cmd/sld-editor/main.go` — loads config, wires up the element library, storage, and API server, and runs the HTTP server.
- `backend/internal/slddoc/` — the diagram document model (`Diagram`/`Layer`/`VoltageClass`/`Node`/`Element`/`Connector`/`Label`), XML `Load`/`Save`, and SVG `Render`. Ported from `sld-svg/internal/slddoc`; extended with JSON tags (for the API), an optional `Editor` block on `Diagram` (grid spacing/snap/showGrid/background) that round-trips through Save/Load and is honored by Render's background color, and `Diagram.LastID` (XML attribute `lastId`) — the high-water mark for the frontend's own autoincrement id counter (see `diagramOps.ts`'s `IdSequence`); the backend itself never assigns or interprets an id, it only round-trips this field. Every id (`Element`/`Node`/`Connector`/`VoltageClass`/`Layer`, and every field referencing one — `Port.Node`, `Element.Voltage`/`Layer`, `Connector.From`/`To`, `Label.For`) is a plain `int`, never a string; 0 doubles as "unset" for an optional reference since a real id is never 0 (`IdSequence` starts at 1). `Element.Shape`/`ElementSymbol.Shape` are the one exception — a symbol-library key like `"41"`, not an assigned identity, so they stay strings. Rendering matches real xsde2svg conventions closely: every selectable element/busbar/connector carries its own bare integer `id` plus `data-name`/`data-voltage`/`data-type` (busbar/connector: a single flat `<polyline>`, no wrapping `<g>`; a `KindObjectLink` connector's own `data-type` is `"21"`, via `connectorTypeCode`, and its own type-comment reads `<!-- Buswork:21 -->` — the same `Name:code` convention an element's own comment uses (`connectorKindName`); symbol elements: `data-voltage`/`data-type` added alongside the pre-existing `data-name` on the outer `<g>`) — confirmed against a real corpus file, `sld-viewer/assets/sld/PS_110kV_Example.svg`. A switching device's state-driven fill path also carries `data-fill="0:red,1:lawngreen,2:yellow"` (a fixed legend, from `Render`'s `stateColorSet`/`StateColor` — see `config.Config.StateColors`) and its state-indicator path carries `data-state="<value>"` when the element has a recorded `State`, matching a real xsde2svg breaker/switch exactly. A `data-editor-kind="element"|"connector"` attribute (this editor's own addition, not part of that format) is what the frontend actually hit-tests against, plus a wider invisible hit-target circle around small symbol geometry — but only in `Render`'s `Interactive` mode. `RenderMode` (`Static`/`Interactive`) controls whether that editor-only markup gets added at all: `Static` is a clean, xsde2svg-faithful document (used for the saved `.svg` and its direct-download endpoint), `Interactive` is for the live in-app canvas only, never written to disk. `id`/`data-name`/`data-voltage`/`data-type`/`data-fill`/`data-state` are present in both modes either way, since a real xsde2svg document carries those regardless.
- `backend/internal/elements/` — loads and merges one or more element-library XML files (shape → class/name/category/SVG template/terminals) into an `Elements` palette catalog and an `internal/slddoc.SymbolLibrary` for rendering. This is the config-driven "add element libraries" mechanism: `elements.libraries` in the YAML config lists the files to merge (later files override earlier ones' shapes), so a site extends the palette by adding a file, not code. `Symbol.Terminals` (optional, `[]slddoc.Point`, parsed from a `<terminals><terminal x="…" y="…"/>…</terminals>` block) is a shape's own real connection points in local/unrotated coordinates, included in `/api/elements`'s response — purely informational (`Canvas` draws a marker at each one on the current selection); it plays no part in what Ctrl/Cmd-click-to-connect actually does.
- `backend/assets/elements/base.xml` — the bundled default element library (17 equipment shapes + a busbar entry), ported from `sld-svg`'s `symbols.xml` with class/name/category metadata added for the palette. The Breaker (shape 41) is the only shape with `<terminals>` defined so far: `(0,-10)`/`(0,10)`, the outer ends of its two stem strokes.
- `backend/internal/storage/` — filesystem-backed diagram store (`List`/`Create`/`Load`/`Save`/`Render`) under the configured diagrams directory (`../diagrams` by default). `Save` always writes both the diagram's `.xml` (source of truth) and a rendered `.svg`; a symbol missing from the configured element libraries is reported back as a non-fatal `renderWarning`, never a failed save.
- `backend/internal/config/` — the app's own `Config` struct (server bind address, log level, diagrams dir, element library paths, editor defaults, default voltage-color palette, global state->color legend), read via `pkg/configuration.Read`. See `backend/config/sld-editor.yaml`. `StateColors` (`state_colors`) is threaded through `storage.New` into every `slddoc.Render` call — unlike `VoltageColors`, it has no per-diagram override; an element only ever records a raw `State` value, never a color.
- `backend/internal/api/` — the Gin HTTP surface: `/api/diagrams` (list/create/get/save), `/api/diagrams/:name/svg` (render), `/api/render` (preview an unsaved diagram), `/api/elements` (palette catalog), `/api/config` (editor + voltage-color + state-color defaults).
- `backend/pkg/configuration/` — reusable YAML + environment-variable config loader. Reads/writes a config struct via `configuration.Read(file, &cfg)`, using `yaml` struct tags for file fields and `env:"true"` tags to opt individual fields into environment-variable overrides (env var name is derived from the field's parent+own `yaml` tags, uppercased, optionally prefixed with `configuration.EnvVarPrefix`).
- `backend/pkg/llog/` — leveled logger built on the standard `log` package (`Trace`/`Debug`/`Info`/`Warning`/`Error`), exposed as a package-level `llog.Logger` singleton with `Errorf`/`Infof`/`Debugf`/`Tracef`/`Warnf` methods gated by `SetLevel`.
- `diagrams/` — default runtime directory for saved diagrams (`.xml`/`.svg` pairs); gitignored except for a `.gitkeep`, since these are user data, not source.
- `frontend/src/state/useDiagramContext.ts` + `DiagramContext.tsx` — the app's single source of truth for the open diagram: current `Diagram`, dirty flag, the diagrams list, the elements catalog, config defaults, selection state (`selectedElementId`/`selectedConnectorId`/`selectedElementIds`, mutually exclusive across kinds — `selectedElementIds` is always a superset of `selectedElementId`, holding every shift-clicked element while `selectedElementId` tracks whichever single one still applies for things that only make sense for one, like Properties' full field editor), `toggleElementSelection` (shift-click add/remove), the armed palette symbol (`armedSymbol`, for click-to-place), `defaultVoltage`/`setDefaultVoltage` (the last voltage class picked in Properties, session-only, seeds a newly placed element/busbar), and the New/Open/Save/Save-As/update/select/arm/delete actions (`deleteSelected` removes the whole `selectedElementIds` set when non-empty). Split into two files (context+hook vs. the `DiagramProvider` component) so the component-only file keeps Vite Fast Refresh working.
- `frontend/src/lib/api.ts` — the only place that calls the backend; normalizes the wire `Diagram` shape (Go nil slices serialize as JSON `null`) to always-arrays before anything else in the app sees it.
- `frontend/src/lib/diagramOps.ts` — pure `Diagram -> Diagram` mutation functions (`placeElement`/`placeBusbar`/`moveElement`/`updateBusbarPoint`/`connectElements`/`removeElement`/`removeConnector`/`copyElement(s)`/`pasteElement(s)`/`add`|`update`|`removeVoltageClass`) that `Canvas`/`PropertiesPanel`/`SettingsPanel` apply through `updateDiagram`; kept separate from the components so the actual editing rules (e.g. what `removeElement` cleans up) are testable/reviewable without any DOM/React involved. New element/node/connector ids come from `IdSequence`, a plain autoincrement counter seeded from `diagram.lastId` (persisted on the diagram — see `Diagram.LastID`'s doc comment); `ensureLastId` backfills a starting value (highest existing numeric id) for a diagram saved before this existed. A pasted element/group is named like a freshly placed one (`"<type>-<id>"`), not `"<name> copy"`; `pasteElements` places a whole copied multi-selection as a rigid group anchored at its own centroid, and both single/group paste take an optional `snap` function applied to each placed point — needed because the midpoint/centroid of two or more on-grid points isn't itself necessarily on-grid, so without it a paste could land off-grid even though its target point was snapped. `symbolTerminals` resolves a shape's own `Terminals` (rotated by the element's `orient`, translated by its `x`/`y`) for `Canvas` to draw as a visual aid — `connectElements` itself never calls it and stays anchor-to-anchor. `drawConnectorPath`/`drawDanglingConnectorPath` are the click-to-route tool's own connector creators: both take an explicit, possibly multi-segment `points` path (and an optional `voltage`, matching `placeElement`/`placeBusbar`'s own — otherwise a freshly drawn wire renders with no color, `Render`'s fallback for one with none) instead of always a straight two-point line; the "dangling" variant ends in mid-air (a Node with no Port referencing it) rather than requiring a second element. `moveConnectorVertex`/`insertConnectorVertex`/`removeConnectorVertex` edit an *already-drawn* connector's own geometry — its two true endpoints are always off-limits (they're what its Nodes/Ports point at), but any interior point can be dragged (a "projection-lock" rule keeps both adjoining segments orthogonal — a movable neighbor slides along whichever axis preserves its own segment's orientation, a fixed-endpoint neighbor gets a new bend inserted next to it instead, since it can't move), inserted (raw, for a double-click-added bend or as the first half of a midpoint-drag), or removed outright (connecting its former neighbors directly, which can leave a diagonal segment if they don't already share an axis — the exact behavior asked for). `simplifyOrthogonalPath` collapses a now-redundant "straight-through" point or an exact duplicate after any of these. `deleteConnectorSegment` cuts a connector at one segment and replaces it with up to two new connectors, each keeping the original's one still-valid end and getting a fresh Node (with no Port referencing it) at the cut — either half is dropped instead if it would end up a single point. `usedNodeIds` collects every Node id some element's Port still references (the same notion of "attached" `removeElement`'s own orphan-cleanup already uses); `danglingConnectorEnds` checks a connector's own two Nodes against that set so `Canvas` can flag/offer to remove whichever end (if any) isn't actually attached to anything. `moveElements` ("Piece C") is `moveElement` for a whole set of ids at once, plus a reroute pass over every connector touching one of their ports: an end whose owning element is in the moving set gets dragged to its new position (both ends moving translates the whole connector as a rigid unit instead, so a wire directly between two co-moving elements doesn't need to bend at all); the segment touching a single moved end is kept orthogonal via the same slide-the-movable-neighbor-or-insert-a-bend-at-a-fixed-one rule `moveConnectorVertex` uses, and the moved end's own Node position is updated to match, same as everywhere else a connector endpoint is created or moved.
- `frontend/src/lib/elementIcon.ts` — turns a palette symbol's raw SVG `template` (now included in `/api/elements`'s response) into markup for a small preview icon, substituting placeholder values that make sense for a static, state-less preview (`{color}` -> `currentColor`, `{state:a|b|c}` -> always `a`, ...) instead of a real instance's own voltage/state.
- `frontend/src/lib/geometry.ts` — `clientToDiagramPoint`/`snapValue`: screen <-> diagram-unit coordinate conversion and grid snapping. `nearestPointOnSegment`/`nearestPointOnPolyline` project a point onto the nearest spot along a multi-vertex polyline (not just its endpoints) — what lets a busbar act as a continuous terminal for the routing tool.
- `frontend/src/components/Sidebar.tsx` — icon rail with four toggles. File/Elements/Settings share one left-docked slot (`activeLeftPanel` in `App.tsx`); Properties docks on the **right** side of the canvas instead and has its own independent `propertiesOpen` state, so it can stay open at the same time as the palette while placing/wiring elements — see `App.tsx`'s `Shell`.
- `frontend/src/components/ContextMenu.tsx` — generic right-click menu (`items: {label, onSelect, disabled?}[]` positioned at a given x/y, backdrop click or Esc to dismiss); `Canvas` is currently its only user, for Copy/Delete/Paste.
- `frontend/src/components/panels/{FilePanel,ElementsPanel,SettingsPanel,PropertiesPanel}.tsx` — File (New/Open/Save/Save As); Elements (palette grouped by category, each button showing a small preview icon via `lib/elementIcon.ts` — click an entry to "arm" it for click-to-place, click again or Esc to cancel); Settings (grid spacing/snap/show-grid/background stored on the diagram's own `editor` block, plus a "Voltage classes" section to add/edit/rename/delete a diagram's own, via `diagramOps.addVoltageClass`/`updateVoltageClass`/`removeVoltageClass`); Properties (element name/voltage class/state-if-switching-device/points-if-busbar-else-orientation, or a connector's kind/voltage, plus a delete button either way — auto-opens the first time something gets selected, via `App.tsx`'s null-to-non-null transition check, without fighting a panel the user closed; a multi-selection of more than one element instead shows just a count and a bulk delete, no per-field editor). Properties' voltage `<select>` (`diagramOps.voltageClassOptions`/`resolveVoltageSelection`) is seeded with the server's default `voltage_colors` presets directly, not just the diagram's own classes — picking one not yet on the diagram creates and assigns it in one action, so a freshly opened diagram (which starts with zero voltage classes) doesn't require a separate trip to Settings first; assigning one also updates `defaultVoltage` (`DiagramContext`) so the next placed element/busbar starts with the same class. The State `<select>` (Breaker/Disconnector/LoadBreakSwitch/GroundSwitch only) is seeded from `config.stateColors` (`GET /api/config`'s `stateColors`, ultimately `config.Config.StateColors`).
- `frontend/src/components/Canvas.tsx` — renders the current in-memory diagram by POSTing it to `/api/render` (debounced) and injecting the returned SVG, wrapped in `react-zoom-pan-pinch` for pan/zoom. Also owns all canvas interactivity: hit-tests clicks against the `data-editor-kind` marker `Render` writes on every selectable node (reading its plain `id` attribute — a DOM id is always a string, so it's parsed back to a number — `Number(hit.id)` — rather than relying on any naming scheme), select/shift-click-to-multi-select/drag-move (grid-snapped; dragging any element already part of a multi-selection moves the whole set together, and any connector attached to whatever moved is rerouted to follow — `diagramOps.moveElements`, committed on mouseup same as the move itself), click-to-place (armed symbol) or drag-to-draw (busbar), Ctrl/Cmd-click-to-connect (`connectElements`, instant anchor-to-anchor), a separate click-to-route tool (`routing` state: click a terminal — `findConnectionTarget`, tight `TERMINAL_HIT_RADIUS` so it doesn't swallow the rest of an element's body — to start, click to bend, orthogonal live preview via `appendOrthogonalPoint` (a delta under `ALIGNMENT_EPSILON` snaps to exactly zero — needed since a busbar target's floating-point-projected coordinate essentially never lands on a whole number, and without this every such connection grew an invisible sub-unit spur segment), click a valid target — another terminal or any point along a busbar, via `nearestPointOnPolyline` — to finish with `diagramOps.drawConnectorPath`, double-click to end in mid-air with `drawDanglingConnectorPath` or, on an existing connector's own line, to add a bend point there instead, Esc to cancel), reshaping an already-selected connector's own geometry (a filled-square handle per interior vertex, a semi-transparent circle per segment midpoint — `handleVertexMouseDown`/`handleMidpointMouseDown`, live-previewed via `connectorPreviewPoints` calling the same pure `diagramOps` functions the eventual mouseup commits; a plain click with no real movement selects just that vertex, via `selectedVertex`, for Delete/Backspace to remove instead of the whole wire), right-click context menu (Copy/Delete/Paste for elements — right-clicking within an existing multi-selection preserves it, so Copy/Delete act on the whole set; Paste places a whole copied group as a rigid unit via `diagramOps.pasteElements` — while a connector instead offers "Delete segment", which uses `nearestSegmentOnPolyline` against the clicked point plus `diagramOps.deleteConnectorSegment` to cut just that segment, and "Delete wire" for the old whole-connector removal), Delete/Backspace/Escape handling, and — while exactly one busbar is selected — a draggable, unfilled red square handle per endpoint (`diagramOps.updateBusbarPoint`, independent of the whole-element drag) for repositioning one point at a time. Selection state is compared with explicit `!== null` checks, not truthiness — an id of 0 must not read as "nothing selected". While dragging, the real backend-rendered symbol's own `transform` (or a busbar's `points`) is mutated directly in the DOM to follow the cursor (`dragElementsInDom`) rather than showing an abstract dashed ghost — cheaper than waiting on the debounced re-render, and it snaps into its real final position exactly where that re-render will confirm it. Selection highlights, a small red 0.5px "X" at each currently-selected element's own real terminal positions (blue/green when hovered or a valid routing target — `connectTarget` state, always tracked on mousemove, purely visual — hidden on whichever element is mid-drag since it's derived from diagram state rather than the DOM `dragElementsInDom` moves), a red dashed outline plus a clickable red-dot marker at each dangling connector end (computed once per render from `diagramOps.usedNodeIds`/`danglingConnectorEnds`; clicking a dot removes that whole connector via `removeConnector`), and the grid-spacing alignment overlay (only drawn when Settings' "Show grid" is on) are all drawn from diagram state as separate `<svg>` layers rather than by touching the injected server-rendered markup — the grid layer specifically has to render *above* that markup, not below, since the backend's rendered SVG paints its own opaque background rect that would otherwise hide a grid placed underneath it.
- `frontend/src/i18n/` — `en.ts` (the string dictionary) + `index.ts` (`t(key, params?)`); every user-facing string should go through a `TranslationKey`, not an inline literal.
- `frontend/src/types/index.ts` — TypeScript types mirroring `backend/internal/slddoc`'s JSON shape and the `elements`/`config` API types; kept in sync by hand (no codegen) when the backend's JSON shape changes.

Both `backend/pkg/configuration` and `backend/pkg/llog` carry their own MIT `LICENSE` files, indicating they're shared utility packages carried over from the author's other projects rather than code written specifically for this repo.
