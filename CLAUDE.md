## What this is

A monorepo SCADA-style Single Line Diagram (SLD) editor for Power/Energy control engineers

## Project state

Stages 1-3 are implemented: backend core API, frontend shell UI, and interactive canvas editing (select/multi-select/drag/click-to-place/click-to-connect/copy-paste/delete). A shape can declare its own real terminal points (`elements.Symbol.Terminals`, so far only the Breaker and the Disconnector, both `(0,-10)`/`(0,10)`) — shown as a small red "X" on the current selection, blue on hover — and `Canvas` now also has a proper click-to-route wiring tool — select is always the default; a plain click only starts a route while a wire kind is armed from the Elements palette's own "Wires" section (`armedWireKind`, shown pressed there while active — the section has a "Wire" button for the plain/default kind alongside Overhead line/Cable line, since something has to be armed for *any* kind now, not just the two named ones) — click a terminal — or Ctrl/Cmd-click any point along a busbar or an already-drawn connector's own line — to start, click to bend, click a target — another terminal, any point along a busbar, or any point along an already-drawn connector's own line — to finish, double-click to end in mid-air, Esc to cancel; a plain click on a busbar/connector still means select/drag or select/reshape as always, since neither has a discrete pin of its own — the Ctrl/Cmd is what disambiguates "start a route here" from that; see `Canvas`'s `routing` state, whose `from` anchor and eventual target are each either an element or a connector tap, and `diagramOps`'s four route-creator combinations: `drawConnectorPath` (element→element), `drawConnectorPathToConnector` (element→connector), `drawConnectorPathFromConnector` (connector→element), `drawConnectorBetweenConnectors` (connector→connector), plus their `...FromPoint`/`...FromPointToConnector`/`drawDanglingConnectorPathFromPoint` siblings for a route *started* by double-clicking empty canvas (`RouteStart`'s third kind, `'point'` — a bare mid-air anchor, nothing attached) — any tap end (element↔connector or point↔connector) splits the connector it lands on into two, sharing a junction Node with the new wire, so it reads as a real electrical connection rather than a merely-visual touch; every one of them takes the new connector's own `ConnectorKind`, defaulting to `BusWork` but overridable by arming one of the Elements palette's own "Wires" buttons first (`armedWireKind`) — the only way to get a `KindOverheadLine`/`CableLine` connector (`BusbarWire` was removed as a palette choice — see the Elements panel bullet below), since a connector's Kind isn't editable after the fact in Properties. `OverheadLine`/`CableLine` also get an auto-generated `Name` ("Overhead line-12", `diagramOps.defaultConnectorName`) other kinds don't) alongside the older instant Ctrl/Cmd-click-connect (`connectElements`, still anchor-to-anchor only, elements only, unchanged — note Ctrl/Cmd-clicking a busbar now starts a route from it instead, taking priority over `connectElements` for that case). An already-drawn connector can also be reshaped directly — select it to get a filled-square handle at each interior bend point and a semi-transparent circle at each segment's own midpoint (drag a vertex to move it orthogonally, drag a midpoint to insert a new bend, double-click the line to add one directly, select a vertex and Delete/Backspace to remove just it; see `diagramOps.moveConnectorVertex`/`insertConnectorVertex`/`removeConnectorVertex`/`simplifyOrthogonalPath`). Deletion also has two granularities now ("Piece B"): right-clicking a connector offers "Delete segment" (splits it into up to two independent connectors at the clicked segment, via `diagramOps.deleteConnectorSegment` — either side is dropped instead if the cut would leave it a single point) alongside "Delete wire" (the old whole-connector removal). A connector end left unreferenced by an element's Port — from a segment cut, or from ending a route in mid-air — is deliberately left unflagged: an earlier version of this editor gave it a persistent red dashed outline plus a one-click-delete red dot, but leaving a wire's end unconnected (to finish later, or on purpose) turned out to be an entirely normal, intentional thing to do, not something needing a warning — that treatment was removed, and an unconnected end today looks and behaves exactly like any other connector, selected/deleted the same ordinary way (Delete/Backspace, or right-click "Delete wire"). Dragging an element (or a multi-selected group) now also re-routes whatever's attached to it ("Piece C", endpoint-follows-only — the simplest useful version, not full accordion re-layout): a connector with both ends on elements moving together translates as a rigid whole, one with only one end attached instead has just that end follow, with the touching segment kept orthogonal the same projection-lock way an interior vertex drag already is (`diagramOps.moveElements`). Not yet built: a 45°/manual-bend-axis routing mode, re-routing when a BusBarSection's own single-endpoint drag handle moves instead of a whole-element drag, and undo/redo. Importing an existing xsde2svg-style SVG is supported: dropping/picking a `.svg` instead of a `.xsld` (App's drop handler / File panel's picker, `DiagramContext.loadDiagramFromFile`, which picks the path by extension) posts it to `POST /api/import/svg`, which runs the sibling `slddoc` module's own `Extract` (the same one `sld-svg`'s `svg-sld extract` CLI uses) with the server's `voltage_colors` presets as voltage hints, and returns `{diagram, report}` (`report.skipped` is a code-sorted `[{code, name, count}]` list, `name` from the sibling module's own `slddoc.ObjectTypeName`). The frontend keeps that report as `DiagramContext.importLog` (cleared by open/new/an `.xsld` import) and shows it in `components/ImportLogDialog.tsx` — opened automatically after each `.svg` import and re-openable from the File panel's "Show import log" button — listing extracted counts, each extracted voltage class with its usage count (`diagramOps.voltageUsage`), skipped types and failed ids. Since `Extract` never sets one, an imported diagram's `editor.defaultVoltage` defaults to its most-used voltage class (`diagramOps.mostUsedVoltage`), changeable from the same dialog's Default voltage picker. A drop/pick goes through `DiagramContext.importDiagramFile` first, not `loadDiagramFromFile` directly: it lists the target folder (`GET /api/diagrams?dir=`, `lib/diagramPath.ts`'s `parentDir`/`baseName`) and, when a diagram of the same name already exists on the server, parks the file as `pendingImport` for `components/ConfirmReloadDialog.tsx` to ask "Reload" (load it anyway — the next Save overwrites the server copy; `confirmPendingImport`) or Cancel (`cancelPendingImport`, the open diagram stays untouched) instead of loading it straight away.

The routing tool can also *start* in mid-air, the same way it can already end there: double-clicking empty canvas (not already routing, and not on an existing connector's own line, which still means "add a bend point" as before) begins a brand new route from a bare point with nothing attached at all — `react-zoom-pan-pinch`'s own default double-click-to-zoom is explicitly disabled (`Canvas`'s `TransformWrapper`, `doubleClick={{disabled: true}}`) so it doesn't fight this. `removeConnector` (`diagramOps.ts`) now also prunes a deleted connector's own from/to Nodes if nothing else references them afterward (no element Port, no other connector) — a real gap before: deleting a wire left its own now-unused endpoint Nodes behind as dead `<node>` entries in the saved XML forever; `deleteConnectorSegment` deliberately still uses a plain filter instead, since it reuses the deleted connector's own from/to for whichever side keeps the original endpoint. `placeElement` now defaults a freshly placed Breaker/Disconnector (either shape) to State 1 ("Close") instead of leaving it unset, matching how most one-line diagrams actually start; LoadBreakSwitch/GroundSwitch are untouched. The browser tab title tracks the open diagram (`${name}${dirty ? ' *' : ''} — SLD Editor`, a `document.title` effect in `DiagramProvider`).

Reference repos on disk that this project's design follows: `sld-svg` (sibling repo) defines the canonical `slddoc` XML format and is the source `internal/slddoc` was ported from (its own copy lives under `sld-svg/internal/`, so it can't be imported across module boundaries — see that package's own doc comment); `sld-viewer` (sibling repo) is the UI/UX and backend-stack reference (React+Vite+TS+Tailwind+lucide-react frontend; Gin+YAML-config backend), though it's a full DB-backed SCADA viewer and much heavier than what this editor needs.

Run the backend from `backend/`: `go run ./cmd/sld-editor -config config/sld-editor.yaml` (binds `0.0.0.0:8090` by default). Build/vet/test: `go build ./...`, `go vet ./...`, `go test ./...`, all from `backend/`. Run a single test: `go test ./internal/slddoc/... -run TestName`. The backend depends on the sibling `slddoc` module (`github.com/PVKonovalov/slddoc` -> `../../slddoc`, via a `replace` directive in `backend/go.mod`), so that repo must be checked out next to this one for any of the above to work.

Run the frontend from `frontend/`: `npm install` once, then `npm run dev` (Vite dev server on `:5173`, proxying `/api` to `:8090` — the backend must already be running; `npm run dev:ru` for the Russian UI locale, picked at build time — see `frontend/src/i18n/`). Type-check + production build: `npm run build` (English, `dist/`), or `npm run build:en`/`npm run build:ru` for an explicit locale build (`dist-en/`/`dist-ru/`).

Production build (from the repo root, not `backend/`/`frontend/`): `make` cross-compiles a single self-contained binary per (OS/arch, locale) combination, with the frontend's own production build embedded directly into the Go binary (`backend/internal/webui`) — no separate static file host needed to deploy it. Targets: `make linux`/`windows`/`macos` (both locales each), or a specific one like `make linux-en`/`make macos-arm64-ru`; `make docker-build` builds the linux+windows targets inside a pinned container instead of requiring a local cross-compile-capable Go toolchain; `make clean`. Binaries land in `build/`. Day-to-day development still uses `go run`/`npm run dev` as above; this is purely for producing deployable binaries. See `README.md` and the root `Makefile` for the full target list.

## Structure

- `backend/cmd/sld-editor/main.go` — loads config, wires up the element library, storage, and API server, and runs the HTTP server.
- `backend/internal/slddoc/` — the diagram document model (`Diagram`/`Layer`/`VoltageClass`/`Node`/`Element`/`Connector`/`Label`), XML `Load`/`Save`, and SVG `Render`. Ported from `sld-svg/internal/slddoc`; extended with JSON tags (for the API), an optional `Editor` block on `Diagram` (grid spacing/snap/showGrid/showNodes/background/defaultVoltage) that round-trips through Save/Load and is honored by Render's background color (`DefaultVoltage`/`ShowNodes` aren't — they're frontend-only concerns the backend just round-trips, same as `LastID`: `DefaultVoltage` seeds what a *newly placed* element/connector starts with, `ShowNodes` toggles Canvas's own debug overlay), and `Diagram.LastID` (XML attribute `lastId`) — the high-water mark for the frontend's own autoincrement id counter (see `diagramOps.ts`'s `IdSequence`); the backend itself never assigns or interprets an id, it only round-trips this field. `Load` also transparently rewrites two stored values still carrying an old form from before this editor changed them, so an already-saved diagram keeps loading and rendering correctly and simply picks up the new value for real the next time it's saved: a Connector's `Kind` from the legacy `"ObjectLink"` to `KindBusWork` (`kindObjectLinkLegacy`), and an Element's `Shape` from the removed duplicate Disconnector shape `"71"` to `"162"` (`shapeDisconnectorLegacy`/`shapeDisconnector`) — this second one only fires on `Load` itself (i.e. opening a saved diagram via `storage.Load`), not on `POST /api/render`'s own plain JSON bind, so a diagram already open in the browser with a stale shape needs reopening, not just a backend restart, to pick it up. Every id (`Element`/`Node`/`Connector`/`VoltageClass`/`Layer`, and every field referencing one — `Port.Node`, `Element.Voltage`/`Layer`, `Connector.From`/`To`, `Label.For`) is a plain `int`, never a string; 0 doubles as "unset" for an optional reference since a real id is never 0 (`IdSequence` starts at 1). `Element.Shape`/`ElementSymbol.Shape` are the one exception — a symbol-library key like `"41"`, not an assigned identity, so they stay strings. Rendering matches real xsde2svg conventions closely: every selectable element/busbar/connector carries its own bare integer `id` plus `data-name`/`data-voltage`/`data-type` (busbar/most connectors: a single flat `<polyline>`, no wrapping `<g>`, no `data-name` at all; a `KindBusWork` connector's own `data-type` is `"21"`, via `connectorTypeCode`, and its own type-comment reads `<!-- Buswork:21 -->` — the same `Name:code` convention an element's own comment uses (`connectorKindName`); symbol elements: `data-voltage`/`data-type` added alongside the pre-existing `data-name` on the outer `<g>`) — confirmed against a real corpus file, `sld-viewer/assets/sld/PS_110kV_Example.svg`. `KindOverheadLine`/`KindCableLine` (`connectorTypeCode`'s `"22"`/`"23"`) are the two connector kinds that break both those patterns: `writeNamedLine` wraps either in a real `<g id data-type data-name data-voltage>` (their `Name` field — the one connector field with no other use, now auto-generated by `diagramOps.defaultConnectorName` when the frontend draws one) around a fixed-1.5-stroke-width polyline. Overhead line's own treatment is confirmed against `sld-viewer/assets/sld/IEEE9bus.svg`'s own xsde2svg-catalog-code documentation and a user-supplied real example matching it byte-for-byte; cable line was given the same treatment for consistency, without its own corpus confirmation. A switching device's state-driven fill path also carries `data-fill="0:red,1:lawngreen,2:yellow"` (a fixed legend, from `Render`'s `stateColorSet`/`StateColor` — see `config.Config.StateColors`) and its state-indicator path carries `data-state="<value>"` when the element has a recorded `State`, matching a real xsde2svg breaker/switch exactly. A `data-editor-kind="element"|"connector"` attribute (this editor's own addition, not part of that format) is what the frontend actually hit-tests against, plus a wider invisible hit-target circle around small symbol geometry — but only in `Render`'s `Interactive` mode. `RenderMode` (`Static`/`Interactive`) controls whether that editor-only markup gets added at all: `Static` is a clean, xsde2svg-faithful document (used for the saved `.svg` and its direct-download endpoint), `Interactive` is for the live in-app canvas only, never written to disk. `id`/`data-name`/`data-voltage`/`data-type`/`data-fill`/`data-state` are present in both modes either way, since a real xsde2svg document carries those regardless. `Label` also carries its own `ID` now (needed so one specific label, not just an Element/Connector, can be individually selected/dragged/deleted in the editor); `writeLabel` takes the same `RenderMode` every other selectable node does, always emitting that `id` on its `<text>` and, `Interactive` only, `data-editor-kind="label"` alongside it — its `<tspan>` continuation lines aren't separately marked, since `closest()` hit-testing against the ancestor `<text>` already covers a click landing on one. `Label.Color`/`VAlign`/`Font` are all optional, empty meaning the original hardcoded look (white fill, baseline-at-Y, Arial) so an already-saved label with none of these attributes keeps rendering exactly as before; `VAlign` (`"top"`/`"middle"`, empty for the original baseline/"bottom") becomes a `dominant-baseline:hanging`/`middle` style, added only when set. `RenderFragments` is `Render`'s incremental-editing counterpart (see TODO.md's own "Reducing frontend/backend traffic" section) — same whole-diagram voltage/topology resolution pass, but only writes markup for a requested `ids []int` (one shared id space across Element/Connector/Label/DigitalDevice, so a plain int works regardless of kind), returned as `map[int]string` instead of written to an `io.Writer`; no type-comment headers or `elementZOrder` tiering (both only meaningful for a full, ordered document — a fragment replaces one already-positioned DOM node in place), and an id no longer in the diagram at all is silently skipped, not an error. `renderElement`/`renderConnector` (the latter factored out of `Render`'s own connectors loop for this) are the shared per-entity dispatch both `Render` and `RenderFragments` call; neither writes its own type-comment any more — the two call sites inside `Render` that want one now write it themselves just before calling in. `ClassTable` (312) is a purely decorative box — reuses Fill/Stroke/StrokeWidth/Points/LineStyle/PropertyText/TextColor entirely, plus (uniquely among Points-based shapes) Orient, which rotates just its own centered label, not the box; `writeTable`/`parseTable` wrap it in a `<g id data-type="312">` (a project-requested change to `xsde2svg/internal/modus/element_312.go` itself — a real instance had no id/grouping of its own at all before that, the same fix already made for shapes 7/106/385/386). `ClassTable2` (313) is a purely decorative multi-row/multi-column grid — new `Element.RowHeights`/`ColumnWidths`/`Cells []TableCell` fields (row/column sizes plus each real cell's own text and optional Fill/TextColor override), deliberately not modeling the real source's own cell-merging or multi-paragraph cell text; `writeTable2` draws each cell as its own bare `<path>` (no per-cell id, matching the real format) inside one wrapping `<g id data-type="313">` — the identical project-requested `element_313.go` change — and `parseTable2` reconstructs row/column boundaries purely from the cells' own drawn rectangle geometry (`tableBoundaries`/`boundaryIndex`), since there's still no row/col index anywhere in the format itself.
- `backend/internal/elements/` — loads and merges one or more element-library XML files (shape → class/name/SVG template/terminals) into an `Elements` palette catalog and an `internal/slddoc.SymbolLibrary` for rendering. This is the config-driven "add element libraries" mechanism: `elements.libraries` in the YAML config lists the files to merge (later files override earlier ones' shapes), so a site extends the palette by adding a file, not code. A `Symbol` carries no grouping/ordering of its own (no `category` attribute any more) — see `config.Config.Palette` below, the single source of truth for where a shape shows up in the Elements panel. `Symbol.Terminals` (optional, `[]slddoc.Point`, parsed from a `<terminals><terminal x="…" y="…"/>…</terminals>` block) is a shape's own real connection points in local/unrotated coordinates, included in `/api/elements`'s response — purely informational (`Canvas` draws a marker at each one on the current selection); it plays no part in what Ctrl/Cmd-click-to-connect actually does. `Library.ValidatePalette` checks every `config.Config.Palette` item (an element shape reference, or a wireKind/special keyword) against the loaded Symbols/fixed keyword vocabulary, called from `main.go` right after loading the libraries — a typo there fails the same "loud at startup" way an unresolvable `elements.libraries` path already does.
- `backend/assets/elements/base.xml` — the bundled default element library (16 equipment shapes + a busbar entry), ported from `sld-svg`'s `symbols.xml` with class/name metadata added for the palette (not category — see above). The Breaker (shape 41) and the Disconnector (shape 162) are the only shapes with `<terminals>` defined so far, both `(0,-10)`/`(0,10)` — the outer ends of their own stem strokes, which happen to land on the same local coordinates for both shapes. `sld-svg/symbols.xml` originally carried a second Disconnector shape, `71`, byte-for-byte identical to `162` (its own comment reads "71 / 162: Disconnector") — removed here since the palette showed it as an indistinguishable duplicate button; `internal/slddoc/render.go`'s `shapeName["71"]` entry is deliberately left in place regardless, so a diagram already carrying a shape-`71` element (from before this, or an external source) still renders with the right label.
- `backend/internal/storage/` — filesystem-backed diagram store (`List`/`Create`/`Load`/`Save`/`Render`/`RenderFragments`) under the configured diagrams directory (`../diagrams` by default). `Save` always writes both the diagram's `.xsld` (source of truth — plain slddoc XML under a dedicated extension, see `slddoc/FORMAT.md`; there is no fallback to the old `.xml` extension) and a rendered `.svg`; a symbol missing from the configured element libraries is reported back as a non-fatal `renderWarning`, never a failed save. A diagram's own "name" is a `/`-separated path relative to that root (e.g. `region1/substation-5`), letting diagrams live in subdirectories — `safeName`/`safePathSegments` validate every segment individually (rejecting empty/`.`/`..`/backslash/whitespace segments, wrapped as `ErrInvalidName`) rather than rejecting `/` outright the way this used to; `Save` (and so `Create`, which calls it) `os.MkdirAll`s the target's own parent directory, so saving/creating under a not-yet-existing folder segment is the only way one gets created — there's no separate "new folder" action. `List(dir string)` replaces the old flat, no-argument `List()` (which used to sort most-recently-modified first): it returns one directory's own immediate contents only (never recurses) as `[]Entry{Name, IsDir, ModTime}` — subdirectories first, then diagrams, each group sorted alphabetically (case-insensitive) — so the File panel's own folder browser fetches one level at a time as the user navigates, the same way a real file browser would. `RenderFragments` is a thin pass-through to `slddoc.RenderFragments` with the store's own `lib`/`defaultFPIText`/`fpiColors`/`stateColors`, the same way `Render` wraps `slddoc.Render`.
- `backend/internal/config/` — the app's own `Config` struct (server bind address, log level, diagrams dir, element library paths, editor defaults, default voltage-color palette, global state->color legend, Elements-panel layout), read via `pkg/configuration.Read`. See `backend/config/sld-editor.yaml`. `StateColors` (`state_colors`) is threaded through `storage.New` into every `slddoc.Render` call — unlike `VoltageColors`, it has no per-diagram override; an element only ever records a raw `State` value, never a color. `Palette` (`palette`) is an ordered list of `PaletteGroup` (`name` + `items`), the single source of truth for the Elements panel's own layout — every group (including the two built-in "Wires"/"Text" ones, not just equipment categories) lives here now, not scattered between `base.xml`'s own per-symbol `category` attribute (removed) and hardcoded frontend JSX. Each item is a bare xsde2svg `ObjectType` code, one single vocabulary for every kind of entry rather than a mix of codes and names: a real element `Shape` (e.g. `"41"`), one of 4 fixed connector-kind codes (`elements.PaletteConnectorKinds` — `"21"`/`"22"`/`"23"`/`"28"` for `BusWork`/`OverheadLine`/`CableLine`/`LinkToObject`, the same codes `internal/slddoc/render.go`'s own `connectorTypeCode` renders a connector's `data-type` from), or Label's/DigitalDevice's own codes (`elements.PaletteLabelShape`/`PaletteDigitalDeviceShape`, `"5"`/`"134"`) — `elements.Library.ValidatePalette` checks every item against those fixed sets or the loaded Symbols, called from `main.go` right after loading the element libraries, so a typo fails loud at startup the same way an unresolvable `elements.libraries` path already does.
- `backend/internal/api/` — the Gin HTTP surface: `GET /api/diagrams?dir=<path>` (list one folder's own contents — `dir` empty/omitted for the store's own root), `POST /api/diagrams` (create — `name` in the JSON body, may itself carry `/` subdirectory segments), `GET /api/diagrams/open?name=<path>`/`PUT /api/diagrams/save?name=<path>` (load/save an existing diagram), `GET /api/diagrams/svg?name=<path>` (render), `/api/render` (preview an unsaved diagram, full document), `/api/render/fragments` (preview, but only the posted `ids`' own fresh markup — see TODO.md's own "Reducing frontend/backend traffic" section and `slddoc.RenderFragments`'s own doc comment; same never-touches-storage contract as `/api/render`), `/api/import/xml`/`/api/import/svg` (parse a locally dropped/picked `.xsld`, or reconstruct a diagram from an xsde2svg-style `.svg` via `slddoc.Extract` — the latter returns `{diagram, report}`), `/api/elements` (palette catalog — shape definitions only, no layout), `/api/config` (editor + voltage-color + state-color defaults + `palette`, the Elements panel's own layout). `name`/`dir` travel as query parameters rather than a Gin `:name` path segment on every one of these — a route param never matches a literal `/`, so a subdirectory-qualified name couldn't reach a `:name`-based handler at all, and a `*name` catch-all would conflict with the `/svg` suffix route in Gin's own router; a query parameter sidesteps both. `storage.ErrInvalidName` (a bad `name`/`dir`) maps to 400, `storage.ErrNotFound` to 404, `storage.ErrExists` (create only) to 409.
- `backend/pkg/configuration/` — reusable YAML + environment-variable config loader. Reads/writes a config struct via `configuration.Read(file, &cfg)`, using `yaml` struct tags for file fields and `env:"true"` tags to opt individual fields into environment-variable overrides (env var name is derived from the field's parent+own `yaml` tags, uppercased, optionally prefixed with `configuration.EnvVarPrefix`).
- `backend/pkg/llog/` — leveled logger built on the standard `log` package (`Trace`/`Debug`/`Info`/`Warning`/`Error`), exposed as a package-level `llog.Logger` singleton with `Errorf`/`Infof`/`Debugf`/`Tracef`/`Warnf` methods gated by `SetLevel`.
- `diagrams/` — default runtime directory for saved diagrams (`.xsld`/`.svg` pairs); gitignored except for a `.gitkeep`, since these are user data, not source.
- `frontend/src/state/useDiagramContext.ts` + `DiagramContext.tsx` — the app's single source of truth for the open diagram: current `Diagram`, dirty flag, the diagrams list, the elements catalog, config defaults, selection state (`selectedElementId`/`selectedConnectorId`/`selectedElementIds`, mutually exclusive across kinds — `selectedElementIds` is always a superset of `selectedElementId`, holding every shift-clicked element while `selectedElementId` tracks whichever single one still applies for things that only make sense for one, like Properties' full field editor), `toggleElementSelection` (shift-click add/remove), the armed palette symbol (`armedSymbol`, for click-to-place) and, mutually exclusive with `armedSymbol` specifically (not with selection — see below), an armed wire kind (`armedWireKind`, from the palette's own "Wires" section — the routing tool's next completed route uses it instead of the default `BusWork`, single-shot: `Canvas` clears it back to `null` itself once that route finishes, the same way `armedSymbol` clears after one placement). Unlike `armedSymbol`, `selectElement`/`selectConnector`/`toggleElementSelection` deliberately *don't* clear `armedWireKind`: starting a route is a tight-radius terminal hit, so a click meant to start one very often lands a few pixels off and selects the whole element instead (same as any plain click would) — if that also cancelled the arm, every near-miss would force a trip back to the palette to re-arm, which is exactly what made it unusable before this was fixed. `armedWireKind` only clears via `armSymbol` itself (genuine mutual exclusion between the two arm mechanisms), `armWireKind`, `Canvas`'s own Esc handler, or a route actually completing, `defaultVoltage`/`setDefaultVoltage` (the last voltage class picked in Properties/Settings/the New Diagram dialog, session-only, seeds a newly placed element/busbar/connector — re-seeded from the diagram's own persisted `editor.defaultVoltage`, if any, every time `openDiagram`/`newDiagram` runs, so a diagram's own saved default takes effect immediately without a trip to Properties/Settings first), and the New/Open/Save/Save-As/update/select/arm/delete actions (`deleteSelected` removes the whole `selectedElementIds` set when non-empty; `newDiagram` takes an optional `defaultVoltageName` — a server voltage-color preset's name — and, when given, turns it into the new diagram's first `VoltageClass` plus its own `editor.defaultVoltage`, then immediately saves a second time so the very first `.xsld` on disk already carries it rather than leaving it merely dirty). `selectedLabelId`/`selectLabel` and `armedLabel`/`armLabel` (the Elements panel's own "Text" button, click-to-place a standalone Label the same way `armedSymbol` places an element) follow the exact same mutual-exclusion rules as their element/connector/wire-kind counterparts — selecting or arming any one of the five (element, connector, label, symbol, wire kind) clears the other four. `currentDir`/`diagrams`/`browseDir` are the File panel's own folder browser: `diagrams` (a `DiagramEntry[]`, replacing the old flat `DiagramInfo[]`) always holds just `currentDir`'s own immediate contents (`GET /api/diagrams?dir=`), never a flattened tree; get this wrong and a freshly drawn wire renders with no color, `Render`'s fallback for a voltage id it can't resolve. `moveConnectorVertex`/`insertConnectorVertex`/`removeConnectorVertex` edit an *already-drawn* connector's own geometry — its two true endpoints are always off-limits (they're what its Nodes/Ports point at), but any interior point can be dragged (a "projection-lock" rule keeps both adjoining segments orthogonal — a movable neighbor slides along whichever axis preserves its own segment's orientation, a fixed-endpoint neighbor gets a new bend inserted next to it instead, since it can't move), inserted (raw, for a double-click-added bend or as the first half of a midpoint-drag), or removed outright (connecting its former neighbors directly, which can leave a diagonal segment if they don't already share an axis — the exact behavior asked for). `simplifyOrthogonalPath` collapses a now-redundant "straight-through" point or an exact duplicate after any of these. `deleteConnectorSegment` cuts a connector at one segment and replaces it with up to two new connectors, each keeping the original's one still-valid end and getting a fresh Node (with no Port referencing it) at the cut — either half is dropped instead if it would end up a single point. `drawConnectorPathToConnector`/`drawConnectorPathFromConnector`/`drawConnectorBetweenConnectors` are `drawConnectorPath`'s counterparts for a route whose finish and/or start point is a point along an *existing connector's own line* rather than an element — built on a shared private helper, `spliceConnectorAt`, which splits a connector into up to two new ones at the tap point (mirroring `deleteConnectorSegment`'s own split, just inserting a junction instead of cutting one out); whichever of the new wire's own ends land there shares that junction Node with both new halves, a real electrical connection — `drawConnectorBetweenConnectors` splices both ends (necessarily two different connectors — guarded) when a route starts *and* ends as a tap. `spliceConnectorAt` special-cases a tapPoint landing exactly on the target connector's own true `from`/`to` endpoint: rather than a real split, it reuses that end's already-existing Node directly and leaves the connector itself untouched — both a correctness fix for any kind (no more redundant zero-length duplicate connector when a tap happens to land exactly on an endpoint) and what makes a `KindOverheadLine` connector's own begin/end-only target set (`Canvas.findConnectionTarget`) a plain node reuse rather than a needless split. `drawDanglingConnectorPathFromConnector` is `drawDanglingConnectorPath`'s counterpart for a route that starts as a connector tap and still ends in mid-air. `moveElements` ("Piece C") is `moveElement` for a whole set of ids at once, plus a reroute pass over every connector touching one of their ports: an end whose owning element is in the moving set gets dragged to its new position (both ends moving translates the whole connector as a rigid unit instead, so a wire directly between two co-moving elements doesn't need to bend at all); the segment touching a single moved end is kept orthogonal via the same slide-the-movable-neighbor-or-insert-a-bend-at-a-fixed-one rule `moveConnectorVertex` uses, and the moved end's own Node position is updated to match, same as everywhere else a connector endpoint is created or moved. `placeLabel`/`moveLabel`/`updateLabel`/`removeLabel` are a standalone text Label's own equivalents of `placeElement`/`moveElement`/(Properties' inline field edit)/`removeElement` — a freshly placed one starts as plain unlinked `"Label"` text (`for` only set when passed one explicitly); A Label (`data-editor-kind="label"`) is hit-tested/selected the same way as an element/connector, click-to-placed the same way `armedSymbol` places an element (`armedLabel`), and dragged the same instant-DOM-first way `dragElementsInDom` moves an element — `dragLabelInDom` sets the live `<text>`'s own `x`/`y` plus each `<tspan>`'s `x` directly, committed to `diagramOps.moveLabel` on mouseup; its selection marker is a plain circle at its own anchor point, not a measured text bounding box, the same minimal-marker convention a connector/busbar's own highlight already uses.
- `frontend/public/` — static files Vite copies verbatim into `dist/` (so also into the embedded production binary): the favicon set, linked from `frontend/index.html`. `favicon.svg` (a busbar with a closed breaker, on the accent blue) is the source; `favicon-16.png`/`favicon-32.png`/`apple-touch-icon.png` are generated from it with `rsvg-convert`, and `favicon.ico` just wraps the 16/32 PNGs — regenerate all of them together if the SVG changes.
- `frontend/src/i18n/` — hand-rolled i18n, not i18next, and picked at *build time*: there's no runtime language switcher. `en.ts` is the canonical, `'feature.field'`-keyed dictionary (`as const`, so `Dictionary = typeof dictionary` carries literal English values — `TranslationKey = keyof Dictionary` is what actually gets reused elsewhere, never the values' own type); `ru.ts` is the Russian translation, typed `Record<keyof Dictionary, string>` so a key added to `en.ts` and left untranslated is a compile error, not a silent runtime fallback to English. `active.ts` is auto-generated by `frontend/scripts/generate-active-locale.mjs <locale>` (re-run by every `dev`/`dev:en`/`dev:ru`/`build`/`build:en`/`build:ru` npm script) to re-export whichever locale's `dictionary` was requested, always alongside `Dictionary`'s own type from `en.ts` regardless of which one; `index.ts` (`t(key, params?)`, plain `{{param}}` substitution) imports only `./active`, never a specific locale directly, so an unselected locale's strings never reach the bundle — confirmed by grepping a `build:ru` bundle for a Russian string and a `build:en` one for its English source, each present only in its own build. Every user-facing string should go through a `TranslationKey`, not an inline literal.
- `frontend/src/types/index.ts` — TypeScript types mirroring `backend/internal/slddoc`'s JSON shape and the `elements`/`config` API types; kept in sync by hand (no codegen) when the backend's JSON shape changes.

Both `backend/pkg/configuration` and `backend/pkg/llog` carry their own MIT `LICENSE` files, indicating they're shared utility packages carried over from the author's other projects rather than code written specifically for this repo.
