## What this is

A monorepo SCADA-style Single Line Diagram (SLD) editor for Power/Energy control engineers

## Project state

Stages 1-3 are implemented: backend core API, frontend shell UI, and interactive canvas editing (select/multi-select/drag/click-to-place/click-to-connect/copy-paste/delete). A shape can declare its own real terminal points (`elements.Symbol.Terminals`, so far only the Breaker and the Disconnector, both `(0,-10)`/`(0,10)`) — shown as a small red "X" on the current selection, blue on hover — and `Canvas` now also has a proper click-to-route wiring tool — select is always the default; a plain click only starts a route while a wire kind is armed from the Elements palette's own "Wires" section (`armedWireKind`, shown pressed there while active — the section has a "Wire" button for the plain/default kind alongside Overhead line/Cable line, since something has to be armed for *any* kind now, not just the two named ones) — click a terminal — or Ctrl/Cmd-click any point along a busbar or an already-drawn connector's own line — to start, click to bend, click a target — another terminal, any point along a busbar, or any point along an already-drawn connector's own line — to finish, double-click to end in mid-air, Esc to cancel; a plain click on a busbar/connector still means select/drag or select/reshape as always, since neither has a discrete pin of its own — the Ctrl/Cmd is what disambiguates "start a route here" from that; see `Canvas`'s `routing` state, whose `from` anchor and eventual target are each either an element or a connector tap, and `diagramOps`'s four route-creator combinations: `drawConnectorPath` (element→element), `drawConnectorPathToConnector` (element→connector), `drawConnectorPathFromConnector` (connector→element), `drawConnectorBetweenConnectors` (connector→connector), plus their `...FromPoint`/`...FromPointToConnector`/`drawDanglingConnectorPathFromPoint` siblings for a route *started* by double-clicking empty canvas (`RouteStart`'s third kind, `'point'` — a bare mid-air anchor, nothing attached) — any tap end (element↔connector or point↔connector) splits the connector it lands on into two, sharing a junction Node with the new wire, so it reads as a real electrical connection rather than a merely-visual touch; every one of them takes the new connector's own `ConnectorKind`, defaulting to `BusWork` but overridable by arming one of the Elements palette's own "Wires" buttons first (`armedWireKind`) — the only way to get a `KindOverheadLine`/`CableLine` connector (`BusbarWire` was removed as a palette choice — see the Elements panel bullet below), since a connector's Kind isn't editable after the fact in Properties. `OverheadLine`/`CableLine` also get an auto-generated `Name` ("Overhead line-12", `diagramOps.defaultConnectorName`) other kinds don't) alongside the older instant Ctrl/Cmd-click-connect (`connectElements`, still anchor-to-anchor only, elements only, unchanged — note Ctrl/Cmd-clicking a busbar now starts a route from it instead, taking priority over `connectElements` for that case). An already-drawn connector can also be reshaped directly — select it to get a filled-square handle at each interior bend point and a semi-transparent circle at each segment's own midpoint (drag a vertex to move it orthogonally, drag a midpoint to insert a new bend, double-click the line to add one directly, select a vertex and Delete/Backspace to remove just it; see `diagramOps.moveConnectorVertex`/`insertConnectorVertex`/`removeConnectorVertex`/`simplifyOrthogonalPath`). Deletion also has two granularities now ("Piece B"): right-clicking a connector offers "Delete segment" (splits it into up to two independent connectors at the clicked segment, via `diagramOps.deleteConnectorSegment` — either side is dropped instead if the cut would leave it a single point) alongside "Delete wire" (the old whole-connector removal). A connector end left unreferenced by an element's Port — from a segment cut, or from ending a route in mid-air — is deliberately left unflagged: an earlier version of this editor gave it a persistent red dashed outline plus a one-click-delete red dot, but leaving a wire's end unconnected (to finish later, or on purpose) turned out to be an entirely normal, intentional thing to do, not something needing a warning — that treatment was removed, and an unconnected end today looks and behaves exactly like any other connector, selected/deleted the same ordinary way (Delete/Backspace, or right-click "Delete wire"). Dragging an element (or a multi-selected group) now also re-routes whatever's attached to it ("Piece C", endpoint-follows-only — the simplest useful version, not full accordion re-layout): a connector with both ends on elements moving together translates as a rigid whole, one with only one end attached instead has just that end follow, with the touching segment kept orthogonal the same projection-lock way an interior vertex drag already is (`diagramOps.moveElements`). Not yet built: a 45°/manual-bend-axis routing mode, re-routing when a BusBarSection's own single-endpoint drag handle moves instead of a whole-element drag, importing an existing xsde2svg-style SVG (sld-svg's `extract` side of the format was deliberately not ported — see `internal/slddoc/doc.go`), and undo/redo.

The routing tool can also *start* in mid-air, the same way it can already end there: double-clicking empty canvas (not already routing, and not on an existing connector's own line, which still means "add a bend point" as before) begins a brand new route from a bare point with nothing attached at all — `react-zoom-pan-pinch`'s own default double-click-to-zoom is explicitly disabled (`Canvas`'s `TransformWrapper`, `doubleClick={{disabled: true}}`) so it doesn't fight this. `removeConnector` (`diagramOps.ts`) now also prunes a deleted connector's own from/to Nodes if nothing else references them afterward (no element Port, no other connector) — a real gap before: deleting a wire left its own now-unused endpoint Nodes behind as dead `<node>` entries in the saved XML forever; `deleteConnectorSegment` deliberately still uses a plain filter instead, since it reuses the deleted connector's own from/to for whichever side keeps the original endpoint. `placeElement` now defaults a freshly placed Breaker/Disconnector (either shape) to State 1 ("Close") instead of leaving it unset, matching how most one-line diagrams actually start; LoadBreakSwitch/GroundSwitch are untouched. The browser tab title tracks the open diagram (`${name}${dirty ? ' *' : ''} — SLD Editor`, a `document.title` effect in `DiagramProvider`).

Reference repos on disk that this project's design follows: `sld-svg` (sibling repo) defines the canonical `slddoc` XML format and is the source `internal/slddoc` was ported from (its own copy lives under `sld-svg/internal/`, so it can't be imported across module boundaries — see that package's own doc comment); `sld-viewer` (sibling repo) is the UI/UX and backend-stack reference (React+Vite+TS+Tailwind+lucide-react frontend; Gin+YAML-config backend), though it's a full DB-backed SCADA viewer and much heavier than what this editor needs.

Run the backend from `backend/`: `go run ./cmd/sld-editor -config config/sld-editor.yaml` (binds `0.0.0.0:8090` by default). Build/vet/test: `go build ./...`, `go vet ./...`, `go test ./...`, all from `backend/`. Run a single test: `go test ./internal/slddoc/... -run TestName`. The backend depends on the sibling `slddoc` module (`github.com/PVKonovalov/slddoc` -> `../../slddoc`, via a `replace` directive in `backend/go.mod`), so that repo must be checked out next to this one for any of the above to work.

Run the frontend from `frontend/`: `npm install` once, then `npm run dev` (Vite dev server on `:5173`, proxying `/api` to `:8090` — the backend must already be running; `npm run dev:ru` for the Russian UI locale, picked at build time — see `frontend/src/i18n/`). Type-check + production build: `npm run build` (English, `dist/`), or `npm run build:en`/`npm run build:ru` for an explicit locale build (`dist-en/`/`dist-ru/`).

Production build (from the repo root, not `backend/`/`frontend/`): `make` cross-compiles a single self-contained binary per (OS/arch, locale) combination, with the frontend's own production build embedded directly into the Go binary (`backend/internal/webui`) — no separate static file host needed to deploy it. Targets: `make linux`/`windows`/`macos` (both locales each), or a specific one like `make linux-en`/`make macos-arm64-ru`; `make docker-build` builds the linux+windows targets inside a pinned container instead of requiring a local cross-compile-capable Go toolchain; `make clean`. Binaries land in `build/`. Day-to-day development still uses `go run`/`npm run dev` as above; this is purely for producing deployable binaries. See `README.md` and the root `Makefile` for the full target list.

## Structure

- `backend/cmd/sld-editor/main.go` — loads config, wires up the element library, storage, and API server, and runs the HTTP server.
- `backend/internal/slddoc/` — the diagram document model (`Diagram`/`Layer`/`VoltageClass`/`Node`/`Element`/`Connector`/`Label`), XML `Load`/`Save`, and SVG `Render`. Ported from `sld-svg/internal/slddoc`; extended with JSON tags (for the API), an optional `Editor` block on `Diagram` (grid spacing/snap/showGrid/showNodes/background/defaultVoltage) that round-trips through Save/Load and is honored by Render's background color (`DefaultVoltage`/`ShowNodes` aren't — they're frontend-only concerns the backend just round-trips, same as `LastID`: `DefaultVoltage` seeds what a *newly placed* element/connector starts with, `ShowNodes` toggles Canvas's own debug overlay), and `Diagram.LastID` (XML attribute `lastId`) — the high-water mark for the frontend's own autoincrement id counter (see `diagramOps.ts`'s `IdSequence`); the backend itself never assigns or interprets an id, it only round-trips this field. `Load` also transparently rewrites two stored values still carrying an old form from before this editor changed them, so an already-saved diagram keeps loading and rendering correctly and simply picks up the new value for real the next time it's saved: a Connector's `Kind` from the legacy `"ObjectLink"` to `KindBusWork` (`kindObjectLinkLegacy`), and an Element's `Shape` from the removed duplicate Disconnector shape `"71"` to `"162"` (`shapeDisconnectorLegacy`/`shapeDisconnector`) — this second one only fires on `Load` itself (i.e. opening a saved diagram via `storage.Load`), not on `POST /api/render`'s own plain JSON bind, so a diagram already open in the browser with a stale shape needs reopening, not just a backend restart, to pick it up. Every id (`Element`/`Node`/`Connector`/`VoltageClass`/`Layer`, and every field referencing one — `Port.Node`, `Element.Voltage`/`Layer`, `Connector.From`/`To`, `Label.For`) is a plain `int`, never a string; 0 doubles as "unset" for an optional reference since a real id is never 0 (`IdSequence` starts at 1). `Element.Shape`/`ElementSymbol.Shape` are the one exception — a symbol-library key like `"41"`, not an assigned identity, so they stay strings. Rendering matches real xsde2svg conventions closely: every selectable element/busbar/connector carries its own bare integer `id` plus `data-name`/`data-voltage`/`data-type` (busbar/most connectors: a single flat `<polyline>`, no wrapping `<g>`, no `data-name` at all; a `KindBusWork` connector's own `data-type` is `"21"`, via `connectorTypeCode`, and its own type-comment reads `<!-- Buswork:21 -->` — the same `Name:code` convention an element's own comment uses (`connectorKindName`); symbol elements: `data-voltage`/`data-type` added alongside the pre-existing `data-name` on the outer `<g>`) — confirmed against a real corpus file, `sld-viewer/assets/sld/PS_110kV_Example.svg`. `KindOverheadLine`/`KindCableLine` (`connectorTypeCode`'s `"22"`/`"23"`) are the two connector kinds that break both those patterns: `writeNamedLine` wraps either in a real `<g id data-type data-name data-voltage>` (their `Name` field — the one connector field with no other use, now auto-generated by `diagramOps.defaultConnectorName` when the frontend draws one) around a fixed-1.5-stroke-width polyline. Overhead line's own treatment is confirmed against `sld-viewer/assets/sld/IEEE9bus.svg`'s own xsde2svg-catalog-code documentation and a user-supplied real example matching it byte-for-byte; cable line was given the same treatment for consistency, without its own corpus confirmation. A switching device's state-driven fill path also carries `data-fill="0:red,1:lawngreen,2:yellow"` (a fixed legend, from `Render`'s `stateColorSet`/`StateColor` — see `config.Config.StateColors`) and its state-indicator path carries `data-state="<value>"` when the element has a recorded `State`, matching a real xsde2svg breaker/switch exactly. A `data-editor-kind="element"|"connector"` attribute (this editor's own addition, not part of that format) is what the frontend actually hit-tests against, plus a wider invisible hit-target circle around small symbol geometry — but only in `Render`'s `Interactive` mode. `RenderMode` (`Static`/`Interactive`) controls whether that editor-only markup gets added at all: `Static` is a clean, xsde2svg-faithful document (used for the saved `.svg` and its direct-download endpoint), `Interactive` is for the live in-app canvas only, never written to disk. `id`/`data-name`/`data-voltage`/`data-type`/`data-fill`/`data-state` are present in both modes either way, since a real xsde2svg document carries those regardless. `Label` also carries its own `ID` now (needed so one specific label, not just an Element/Connector, can be individually selected/dragged/deleted in the editor); `writeLabel` takes the same `RenderMode` every other selectable node does, always emitting that `id` on its `<text>` and, `Interactive` only, `data-editor-kind="label"` alongside it — its `<tspan>` continuation lines aren't separately marked, since `closest()` hit-testing against the ancestor `<text>` already covers a click landing on one. `Label.Color`/`VAlign`/`Font` are all optional, empty meaning the original hardcoded look (white fill, baseline-at-Y, Arial) so an already-saved label with none of these attributes keeps rendering exactly as before; `VAlign` (`"top"`/`"middle"`, empty for the original baseline/"bottom") becomes a `dominant-baseline:hanging`/`middle` style, added only when set.
- `backend/internal/elements/` — loads and merges one or more element-library XML files (shape → class/name/category/SVG template/terminals) into an `Elements` palette catalog and an `internal/slddoc.SymbolLibrary` for rendering. This is the config-driven "add element libraries" mechanism: `elements.libraries` in the YAML config lists the files to merge (later files override earlier ones' shapes), so a site extends the palette by adding a file, not code. `Symbol.Terminals` (optional, `[]slddoc.Point`, parsed from a `<terminals><terminal x="…" y="…"/>…</terminals>` block) is a shape's own real connection points in local/unrotated coordinates, included in `/api/elements`'s response — purely informational (`Canvas` draws a marker at each one on the current selection); it plays no part in what Ctrl/Cmd-click-to-connect actually does.
- `backend/assets/elements/base.xml` — the bundled default element library (16 equipment shapes + a busbar entry), ported from `sld-svg`'s `symbols.xml` with class/name/category metadata added for the palette. The Breaker (shape 41) and the Disconnector (shape 162) are the only shapes with `<terminals>` defined so far, both `(0,-10)`/`(0,10)` — the outer ends of their own stem strokes, which happen to land on the same local coordinates for both shapes. `sld-svg/symbols.xml` originally carried a second Disconnector shape, `71`, byte-for-byte identical to `162` (its own comment reads "71 / 162: Disconnector") — removed here since the palette showed it as an indistinguishable duplicate button; `internal/slddoc/render.go`'s `shapeName["71"]` entry is deliberately left in place regardless, so a diagram already carrying a shape-`71` element (from before this, or an external source) still renders with the right label.
- `backend/internal/storage/` — filesystem-backed diagram store (`List`/`Create`/`Load`/`Save`/`Render`) under the configured diagrams directory (`../diagrams` by default). `Save` always writes both the diagram's `.xml` (source of truth) and a rendered `.svg`; a symbol missing from the configured element libraries is reported back as a non-fatal `renderWarning`, never a failed save.
- `backend/internal/config/` — the app's own `Config` struct (server bind address, log level, diagrams dir, element library paths, editor defaults, default voltage-color palette, global state->color legend), read via `pkg/configuration.Read`. See `backend/config/sld-editor.yaml`. `StateColors` (`state_colors`) is threaded through `storage.New` into every `slddoc.Render` call — unlike `VoltageColors`, it has no per-diagram override; an element only ever records a raw `State` value, never a color.
- `backend/internal/api/` — the Gin HTTP surface: `/api/diagrams` (list/create/get/save), `/api/diagrams/:name/svg` (render), `/api/render` (preview an unsaved diagram), `/api/elements` (palette catalog), `/api/config` (editor + voltage-color + state-color defaults).
- `backend/pkg/configuration/` — reusable YAML + environment-variable config loader. Reads/writes a config struct via `configuration.Read(file, &cfg)`, using `yaml` struct tags for file fields and `env:"true"` tags to opt individual fields into environment-variable overrides (env var name is derived from the field's parent+own `yaml` tags, uppercased, optionally prefixed with `configuration.EnvVarPrefix`).
- `backend/pkg/llog/` — leveled logger built on the standard `log` package (`Trace`/`Debug`/`Info`/`Warning`/`Error`), exposed as a package-level `llog.Logger` singleton with `Errorf`/`Infof`/`Debugf`/`Tracef`/`Warnf` methods gated by `SetLevel`.
- `diagrams/` — default runtime directory for saved diagrams (`.xml`/`.svg` pairs); gitignored except for a `.gitkeep`, since these are user data, not source.
- `frontend/src/state/useDiagramContext.ts` + `DiagramContext.tsx` — the app's single source of truth for the open diagram: current `Diagram`, dirty flag, the diagrams list, the elements catalog, config defaults, selection state (`selectedElementId`/`selectedConnectorId`/`selectedElementIds`, mutually exclusive across kinds — `selectedElementIds` is always a superset of `selectedElementId`, holding every shift-clicked element while `selectedElementId` tracks whichever single one still applies for things that only make sense for one, like Properties' full field editor), `toggleElementSelection` (shift-click add/remove), the armed palette symbol (`armedSymbol`, for click-to-place) and, mutually exclusive with `armedSymbol` specifically (not with selection — see below), an armed wire kind (`armedWireKind`, from the palette's own "Wires" section — the routing tool's next completed route uses it instead of the default `BusWork`, single-shot: `Canvas` clears it back to `null` itself once that route finishes, the same way `armedSymbol` clears after one placement). Unlike `armedSymbol`, `selectElement`/`selectConnector`/`toggleElementSelection` deliberately *don't* clear `armedWireKind`: starting a route is a tight-radius terminal hit, so a click meant to start one very often lands a few pixels off and selects the whole element instead (same as any plain click would) — if that also cancelled the arm, every near-miss would force a trip back to the palette to re-arm, which is exactly what made it unusable before this was fixed. `armedWireKind` only clears via `armSymbol` itself (genuine mutual exclusion between the two arm mechanisms), `armWireKind`, `Canvas`'s own Esc handler, or a route actually completing, `defaultVoltage`/`setDefaultVoltage` (the last voltage class picked in Properties/Settings/the New Diagram dialog, session-only, seeds a newly placed element/busbar/connector — re-seeded from the diagram's own persisted `editor.defaultVoltage`, if any, every time `openDiagram`/`newDiagram` runs, so a diagram's own saved default takes effect immediately without a trip to Properties/Settings first), and the New/Open/Save/Save-As/update/select/arm/delete actions (`deleteSelected` removes the whole `selectedElementIds` set when non-empty; `newDiagram` takes an optional `defaultVoltageName` — a server voltage-color preset's name — and, when given, turns it into the new diagram's first `VoltageClass` plus its own `editor.defaultVoltage`, then immediately saves a second time so the very first `.xml` on disk already carries it rather than leaving it merely dirty). `selectedLabelId`/`selectLabel` and `armedLabel`/`armLabel` (the Elements panel's own "Text" button, click-to-place a standalone Label the same way `armedSymbol` places an element) follow the exact same mutual-exclusion rules as their element/connector/wire-kind counterparts — selecting or arming any one of the five (element, connector, label, symbol, wire kind) clears the other four. Split into two files (context+hook vs. the `DiagramProvider` component) so the component-only file keeps Vite Fast Refresh working.
- `frontend/src/lib/api.ts` — the only place that calls the backend; normalizes the wire `Diagram` shape (Go nil slices serialize as JSON `null`) to always-arrays before anything else in the app sees it.
- `frontend/src/lib/diagramOps.ts` — pure `Diagram -> Diagram` mutation functions (`placeElement`/`placeBusbar`/`moveElement`/`updateBusbarPoint`/`connectElements`/`removeElement`/`removeConnector`/`copyElement(s)`/`pasteElement(s)`/`add`|`update`|`removeVoltageClass`) that `Canvas`/`PropertiesPanel`/`SettingsPanel` apply through `updateDiagram`; kept separate from the components so the actual editing rules (e.g. what `removeElement` cleans up) are testable/reviewable without any DOM/React involved. New element/node/connector ids come from `IdSequence`, a plain autoincrement counter seeded from `diagram.lastId` (persisted on the diagram — see `Diagram.LastID`'s doc comment); `ensureLastId` backfills a starting value (highest existing numeric id) for a diagram saved before this existed, and — independently, since the two gaps can each exist without the other, as `PS_110kV_Example.xml` did (a real `lastId` from its elements/connectors, but all 303 of its labels still sharing id 0 since Label predates having its own id) — always gives a fresh, unique id to any Label still at 0, so per-label select/drag/edit/delete (which key off `l.id === id`) doesn't end up applying to every label that shares 0 at once; `DiagramContext.openDiagram` flags the diagram dirty when this backfill actually changed anything (comparing object identity: `ensureLastId` returns the same reference when there's nothing to fix), since otherwise the fix only lived in that browser session and reopening the same file reintroduced it. A pasted element/group is named like a freshly placed one (`"<type>-<id>"`), not `"<name> copy"`; `pasteElements` places a whole copied multi-selection as a rigid group anchored at its own centroid, and both single/group paste take an optional `snap` function applied to each placed point — needed because the midpoint/centroid of two or more on-grid points isn't itself necessarily on-grid, so without it a paste could land off-grid even though its target point was snapped. `symbolTerminals` resolves a shape's own `Terminals` (rotated by the element's `orient`, translated by its `x`/`y`) for `Canvas` to draw as a visual aid — `connectElements` itself never calls it and stays anchor-to-anchor. `drawConnectorPath`/`drawDanglingConnectorPath` are the click-to-route tool's own connector creators: both take an explicit, possibly multi-segment `points` path instead of always a straight two-point line; the "dangling" variant ends in mid-air (a Node with no Port referencing it) rather than requiring a second element. A new connector's voltage (all three creators, including `connectElements`) comes from whichever of its `from`/`to` elements already has one — it's electrically joining them, so it should read as their shared voltage, not some unrelated value — falling back to a `defaultVoltage` param (`drawConnectorPath`/`drawDanglingConnectorPath` only, matching `placeElement`/`placeBusbar`'s own seed) only when neither end has one at all; get this wrong and a freshly drawn wire renders with no color, `Render`'s fallback for a voltage id it can't resolve. `moveConnectorVertex`/`insertConnectorVertex`/`removeConnectorVertex` edit an *already-drawn* connector's own geometry — its two true endpoints are always off-limits (they're what its Nodes/Ports point at), but any interior point can be dragged (a "projection-lock" rule keeps both adjoining segments orthogonal — a movable neighbor slides along whichever axis preserves its own segment's orientation, a fixed-endpoint neighbor gets a new bend inserted next to it instead, since it can't move), inserted (raw, for a double-click-added bend or as the first half of a midpoint-drag), or removed outright (connecting its former neighbors directly, which can leave a diagonal segment if they don't already share an axis — the exact behavior asked for). `simplifyOrthogonalPath` collapses a now-redundant "straight-through" point or an exact duplicate after any of these. `deleteConnectorSegment` cuts a connector at one segment and replaces it with up to two new connectors, each keeping the original's one still-valid end and getting a fresh Node (with no Port referencing it) at the cut — either half is dropped instead if it would end up a single point. `drawConnectorPathToConnector`/`drawConnectorPathFromConnector`/`drawConnectorBetweenConnectors` are `drawConnectorPath`'s counterparts for a route whose finish and/or start point is a point along an *existing connector's own line* rather than an element — built on a shared private helper, `spliceConnectorAt`, which splits a connector into up to two new ones at the tap point (mirroring `deleteConnectorSegment`'s own split, just inserting a junction instead of cutting one out); whichever of the new wire's own ends land there shares that junction Node with both new halves, a real electrical connection — `drawConnectorBetweenConnectors` splices both ends (necessarily two different connectors — guarded) when a route starts *and* ends as a tap. `spliceConnectorAt` special-cases a tapPoint landing exactly on the target connector's own true `from`/`to` endpoint: rather than a real split, it reuses that end's already-existing Node directly and leaves the connector itself untouched — both a correctness fix for any kind (no more redundant zero-length duplicate connector when a tap happens to land exactly on an endpoint) and what makes a `KindOverheadLine` connector's own begin/end-only target set (`Canvas.findConnectionTarget`) a plain node reuse rather than a needless split. `drawDanglingConnectorPathFromConnector` is `drawDanglingConnectorPath`'s counterpart for a route that starts as a connector tap and still ends in mid-air. `moveElements` ("Piece C") is `moveElement` for a whole set of ids at once, plus a reroute pass over every connector touching one of their ports: an end whose owning element is in the moving set gets dragged to its new position (both ends moving translates the whole connector as a rigid unit instead, so a wire directly between two co-moving elements doesn't need to bend at all); the segment touching a single moved end is kept orthogonal via the same slide-the-movable-neighbor-or-insert-a-bend-at-a-fixed-one rule `moveConnectorVertex` uses, and the moved end's own Node position is updated to match, same as everywhere else a connector endpoint is created or moved. `placeLabel`/`moveLabel`/`updateLabel`/`removeLabel` are a standalone text Label's own equivalents of `placeElement`/`moveElement`/(Properties' inline field edit)/`removeElement` — a freshly placed one starts as plain unlinked `"Label"` text (`for` only set when passed one explicitly); `For` is saved as a plain reference to an Element's id, informational only like `Connector.Name`, not a live link — dragging the referenced element doesn't move the label along with it. `placeElement` also gives a freshly placed Lamp its own real defaults (`LAMP_DEFAULTS`: `state: 0`, `fillOff: 'none'`, `fillOn: 'red'`, `radius: 11`) instead of leaving all three unset (an unset `radius` renders as an invisible `r="0"` circle), and skips seeding it with `defaultVoltage` the way every other placed symbol gets — a Lamp is a plain indicator read by its own fixed FillOff/FillOn colors, not something with a primary voltage of its own.
- `frontend/src/lib/elementIcon.ts` — turns a palette symbol's raw SVG `template` (now included in `/api/elements`'s response) into markup for a small preview icon, substituting placeholder values that make sense for a static, state-less preview (`{color}` -> `currentColor`, `{state:a|b|c}` -> always `a`, ...) instead of a real instance's own voltage/state.
- `frontend/src/lib/geometry.ts` — `clientToDiagramPoint`/`snapValue`: screen <-> diagram-unit coordinate conversion and grid snapping. `nearestPointOnSegment`/`nearestPointOnPolyline`/`nearestSegmentOnPolyline` project a point onto the nearest spot along a multi-vertex polyline (not just its endpoints) — what lets a busbar or an existing connector act as a continuous terminal for the routing tool. `snapPointOnSegment` grid-aligns such a projected point along whichever axis the tapped segment runs freely on (keeping the other axis fixed at the segment's own coordinate, so the result stays exactly on the line) when grid snapping is on — a diagonal segment is left as the raw projection, since it generally can't be grid-aligned while staying on the line.
- `frontend/src/components/Sidebar.tsx` — icon rail with four toggles. File/Elements/Settings share one left-docked slot (`activeLeftPanel` in `App.tsx`); Properties docks on the **right** side of the canvas instead and has its own independent `propertiesOpen` state, so it can stay open at the same time as the palette while placing/wiring elements — see `App.tsx`'s `Shell`.
- `frontend/src/components/ContextMenu.tsx` — generic right-click menu (`items: {label, onSelect, disabled?}[]` positioned at a given x/y, backdrop click or Esc to dismiss); `Canvas` is currently its only user, for Copy/Delete/Paste.

- `frontend/src/components/Canvas.tsx` — renders the current in-memory diagram by POSTing it to `/api/render` (debounced) and injecting the returned SVG, wrapped in `react-zoom-pan-pinch` for pan/zoom. Also owns all canvas interactivity: hit-tests clicks against the `data-editor-kind` marker `Render` writes on every selectable node (reading its plain `id` attribute — a DOM id is always a string, so it's parsed back to a number — `Number(hit.id)` — rather than relying on any naming scheme), select/shift-click-to-multi-select/drag-move (grid-snapped; dragging any element already part of a multi-selection moves the whole set together, and any connector attached to whatever moved is rerouted to follow — `diagramOps.moveElements`, committed on mouseup same as the move itself), click-to-place (armed symbol) or drag-to-draw (busbar), Ctrl/Cmd-click-to-connect (`connectElements`, instant anchor-to-anchor, elements only, always `BusWork`), a separate click-to-route tool (`routing` state — select is always the default: starting one at all, by any means (plain click on a terminal, Ctrl/Cmd-click on a busbar/connector, or double-click on empty canvas), requires `armedWireKind` truthy first — with nothing armed, `handleMouseDown`'s own start-check is skipped entirely and a click just falls through to ordinary select/drag, and `handleWrapperMouseMove`'s hover target-highlight (`connectTarget`) doesn't even compute one, so there's no "you could connect here" indicator implying otherwise; its own resulting connector's Kind is `armedWireKind` itself — `Canvas` clears it back to `null` the moment a route completes, single-shot like `armedSymbol`: click a terminal, or Ctrl/Cmd-click any point along a busbar or an already-drawn connector's own line, to start (`findConnectionTarget`, tight `TERMINAL_HIT_RADIUS` for a plain terminal click; the Ctrl/Cmd modifier is what additionally allows a busbar/connector, whose whole length would otherwise match every click and swallow ordinary select/drag there), click to bend, orthogonal live preview via `appendOrthogonalPoint` (a delta under `ALIGNMENT_EPSILON` snaps to exactly zero — needed since a busbar/connector target's floating-point-projected coordinate essentially never lands on a whole number, and without this every such connection grew an invisible sub-unit spur segment), click a valid target — another terminal, any point along a busbar, any point along an already-drawn connector's own line (tapping into it as a junction) *except* a `KindOverheadLine` connector, which only offers its own two true begin/end points (same tight `TERMINAL_HIT_RADIUS` an element's own terminal uses, not the loose "anywhere on the line" search — an overhead line can't be tapped mid-span) — all via `findConnectionTarget`'s `nearestPointOnPolyline`/`nearestSegmentOnPolyline` search — to finish with whichever of `diagramOps.drawConnectorPath`/`drawConnectorPathToConnector`/`drawConnectorPathFromConnector`/`drawConnectorBetweenConnectors`/`drawConnectorPathFromPoint`/`drawConnectorPathFromPointToConnector` matches the start/target kind pair, double-click to end in mid-air with `drawDanglingConnectorPath`/`drawDanglingConnectorPathFromConnector`/`drawDanglingConnectorPathFromPoint` — or, on an existing connector's own line while *not* routing, to add a bend point there instead, or, on truly empty canvas while *not* routing, to *start* a new route from a bare mid-air point (`RouteStart`'s `'point'` kind — `react-zoom-pan-pinch`'s own default double-click-zoom is disabled, `doubleClick={{disabled: true}}`, so it doesn't fight this) — Esc to cancel), reshaping an already-selected connector's own geometry (a filled-square handle per interior vertex, a semi-transparent circle per segment midpoint — `handleVertexMouseDown`/`handleMidpointMouseDown`, live-previewed via `connectorPreviewPoints` calling the same pure `diagramOps` functions the eventual mouseup commits; a plain click with no real movement selects just that vertex, via `selectedVertex`, for Delete/Backspace to remove instead of the whole wire), right-click context menu (Copy/Delete/Paste for elements — right-clicking within an existing multi-selection preserves it, so Copy/Delete act on the whole set; Paste places a whole copied group as a rigid unit via `diagramOps.pasteElements` — while a connector instead offers "Delete segment", which uses `nearestSegmentOnPolyline` against the clicked point plus `diagramOps.deleteConnectorSegment` to cut just that segment, and "Delete wire" for the old whole-connector removal), Delete/Backspace/Escape handling, and — while exactly one busbar is selected — a draggable, unfilled red square handle per endpoint (`diagramOps.updateBusbarPoint`, independent of the whole-element drag) for repositioning one point at a time. Selection state is compared with explicit `!== null` checks, not truthiness — an id of 0 must not read as "nothing selected". While dragging, the real backend-rendered symbol's own `transform` (or a busbar's `points`) is mutated directly in the DOM to follow the cursor (`dragElementsInDom`) rather than showing an abstract dashed ghost — cheaper than waiting on the debounced re-render, and it snaps into its real final position exactly where that re-render will confirm it. Selection highlights, a small red 0.5px "X" at each currently-selected element's own real terminal positions (blue/green when hovered or a valid routing target — `connectTarget` state, always tracked on mousemove, purely visual — hidden on whichever element is mid-drag since it's derived from diagram state rather than the DOM `dragElementsInDom` moves), a thinner red 0.25px "X" at every `Diagram.Node`'s own position regardless of selection (Settings' "Show nodes" debug overlay, on by default — the real electrical graph, as opposed to the selected-terminal marks' own symbol-declared points), and the grid-spacing alignment overlay (a 0.5px-radius dot at each grid intersection, only drawn when Settings' "Show grid" is on) are all drawn from diagram state as separate `<svg>` layers rather than by touching the injected server-rendered markup — the grid layer specifically has to render *above* that markup, not below, since the backend's rendered SVG paints its own opaque background rect that would otherwise hide a grid placed underneath it. A Label (`data-editor-kind="label"`) is hit-tested/selected the same way as an element/connector, click-to-placed the same way `armedSymbol` places an element (`armedLabel`), and dragged the same instant-DOM-first way `dragElementsInDom` moves an element — `dragLabelInDom` sets the live `<text>`'s own `x`/`y` plus each `<tspan>`'s `x` directly, committed to `diagramOps.moveLabel` on mouseup; its selection marker is a plain circle at its own anchor point, not a measured text bounding box, the same minimal-marker convention a connector/busbar's own highlight already uses.
- `frontend/src/i18n/` — hand-rolled i18n, not i18next, and picked at *build time*: there's no runtime language switcher. `en.ts` is the canonical, `'feature.field'`-keyed dictionary (`as const`, so `Dictionary = typeof dictionary` carries literal English values — `TranslationKey = keyof Dictionary` is what actually gets reused elsewhere, never the values' own type); `ru.ts` is the Russian translation, typed `Record<keyof Dictionary, string>` so a key added to `en.ts` and left untranslated is a compile error, not a silent runtime fallback to English. `active.ts` is auto-generated by `frontend/scripts/generate-active-locale.mjs <locale>` (re-run by every `dev`/`dev:en`/`dev:ru`/`build`/`build:en`/`build:ru` npm script) to re-export whichever locale's `dictionary` was requested, always alongside `Dictionary`'s own type from `en.ts` regardless of which one; `index.ts` (`t(key, params?)`, plain `{{param}}` substitution) imports only `./active`, never a specific locale directly, so an unselected locale's strings never reach the bundle — confirmed by grepping a `build:ru` bundle for a Russian string and a `build:en` one for its English source, each present only in its own build. Every user-facing string should go through a `TranslationKey`, not an inline literal.
- `frontend/src/types/index.ts` — TypeScript types mirroring `backend/internal/slddoc`'s JSON shape and the `elements`/`config` API types; kept in sync by hand (no codegen) when the backend's JSON shape changes.

Both `backend/pkg/configuration` and `backend/pkg/llog` carry their own MIT `LICENSE` files, indicating they're shared utility packages carried over from the author's other projects rather than code written specifically for this repo.
